Merger Assessment

PR #426 was the correct first move. It made a downloaded Studio more useful by turning CLI Health failures into concrete local setup artifacts. It did not yet satisfy the full user goal because the GUI still cannot run those setup steps in a controlled way.

What #426 proves

Studio can detect CLI, repo, Python, and host state, then generate auditable PowerShell setup scripts into dogfood evidence without adding broad Tauri plugin permissions.

What remains open

The GUI cannot yet run preflight, Python install, CLI build, or env configuration. The next slice must add typed, allowlisted execution from Studio.

What must not happen

Do not add a generic shell plugin, provider API path, default source inclusion, or false enforcement claim. Every bootstrap action must be explicit, local, and evidence-recorded.

Dossier Integration

The dossier's core finding is that the current Studio is broad but shallow: many panels run real commands, but too often dump stdout instead of rendering structured Garnet contracts. The next design arc must correct that.

Operating principle

Render the contracts, do not dump stdout. The CLI owns the verdicts. The webview renders structured data and must not recompute trust bands, safety claims, or enforcement status.

Plan Of Attack

The work should be sliced so each PR is reviewable and independently dogfoodable. Phase 0 remains the next practical Windows slice. Phases 1-5 are the dossier-driven Studio redesign sequence.

0

GUI Bootstrap Runner

Turn generated setup scripts into typed, allowlisted GUI actions.

  • Add `studio_bootstrap_run_step` with `preflight`, `install-python`, `build-cli`, and `configure-env` only.
  • Run PowerShell through `run_process_with_timeout`; no Tauri shell plugin.
  • Create `bootstrap-run` evidence bundles with full stdout/stderr and command manifest.
  • Add repo path validation for build/configure steps.
  • Add frontend buttons and clear local-action copy.
1

Dead-Weight And Honesty Cleanup

Apply the dossier's cleanup without breaking existing command coverage.

  • Remove or demote static surfaces only after tests assert replacements.
  • Replace stale hard-coded status tiles with live truth data or remove them.
  • Relabel advisory flows as local evidence only.
2

Diff-Caps Review Gate

Make the unique Garnet trust surface visible in one screen.

  • Wrap `garnet diff-caps --machine` and render its schema directly.
  • Show gained caps, lost caps, band, verdict, and refusal reasons.
  • Display the caveat: no declared widening does not prove absence of undeclared authority.
  • Never compute the band in TypeScript.
3

Velocity Editor

Give Studio a daily-use loop without pretending to be a full IDE.

  • Add a buffer and debounced `garnet check --format json` path.
  • Render diagnostics from JSON with honest span precision.
  • Add capability gutter hints derived only from CLI diagnostics.
  • Do not seal or dogfood every keystroke by default.
4

Enforced/Declared Legend

Make calibrated honesty visible across every Studio panel.

  • Generate status from source or CLI-reported truth, not hand-written HTML.
  • Show `@caps` and `@max_depth` as enforced only where trap evidence exists.
  • Show declared-only bounds and platform sandbox claims as declared or deferred.
5

Agent-Loop Console

Compose the trust cockpit into the agent-supervision surface.

  • Render an `agent-loop --record-dir` dossier as a four-gate pipeline.
  • Reuse the diff-caps card as the authority gate drill-down.
  • Add caps-log and seal panels as structured dossier views.
  • Keep human approval, widening, and seal provenance visibly separate.

Seven-Pass Workflow Loop

The next implementation should use this review loop before PR creation. "Judge" checks whether the feature advances the product. "Auditor" checks whether the evidence and honesty boundaries are defensible.

Pass Judge Auditor Required evidence
1. Product fit Does this make a downloaded Studio meaningfully more usable? Does the copy avoid overselling install success? UI screenshot or e2e selectors plus health-plan behavior.
2. Security Is the action explicit and understandable? No generic shell/open/fs plugin; only typed Rust command execution. Capability JSON still `core:default`; Cargo lacks shell plugin.
3. Command contract Does the API map to user intent? Step IDs are allowlisted; repo paths are validated. Rust unit tests for allowlist and repo validation.
4. Evidence Can the operator see what happened? Full streams are saved before UI truncation. `bootstrap-run` evidence bundle with manifest and command output.
5. Windows UX Can a Windows user recover from missing CLI/Python/repo? Failures explain next action without claiming completion. Playwright e2e and local Studio smoke.
6. Test proportion Is code substance covered by meaningful tests? Tests cover behavior, not only strings. Python contract, Rust unit, npm build, e2e, Studio smoke.
7. Mac handoff Is the macOS continuation clear? Does not claim Mac parity until Mac runner is tested. HTML handoff with explicit Mac continuation tasks.
