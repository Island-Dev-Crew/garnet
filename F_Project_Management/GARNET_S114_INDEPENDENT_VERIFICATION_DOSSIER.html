I · Why this is existential

The one sentence Garnet is staked on

Garnet stakes its entire existence on ONE sentence: "a project can autonomously ACCEPT an agent-authored change and REFUSE a silent authority expansion — the refusal a TRUE gate failure (exit 1), enforced by the runtime kernel." Every individual pillar Garnet uses is precedented elsewhere — capability annotations (Austral/E/Koka), attestation (in-toto/Sigstore), sandboxing (Wasmtime/seccomp). The ONLY defensible novelty is the integration: a sealed capability-diff acceptance gate wrapped around an autonomous agent loop, applied to UNTRUSTED agent-authored code, that dogfoods itself. That novelty claim is empty without independent confirmation, because the threat model IS adversarial code authorship and the S114 red-team was authored end-to-end by a Claude fleet — the same lineage that wrote the kernel it attacks shares blind spots by construction. Rust memory safety is believed not because Mozilla asserted it but because of an independent dynamic oracle (Miri), a machine-checked model (RustBelt), a decade of adversarial ecosystem pressure, and an honestly-policed boundary (unsafe). Garnet has the deterministic traps + regression tests (elements 3-5 at prototype grade) and a partial equivalence trap (element 6 one-directional), but it has NOT cleared the independence bar (element 1) or full surface=enforcement equivalence. S114-independent is the step that converts "we red-teamed it" (marketing) into "a party with no shared state, motivated to break it, re-derived the attack surface and could not silently widen authority" (credible). For a language whose whole value proposition is accepting code you cannot read, self-attested enforcement is security theater. Getting S114 right — genuinely independent, non-circular, honestly scoped — is the difference between Garnet being citable beside Rust and being unfalsifiable vendor assertion. It is existential, not nice-to-have, because Garnet has no other moat.

III · The bar & the field

What “getting it right” means against Rust, E, Austral, WASI

PURPOSE: Garnet is a research-grade capability-secure language built for one thesis — capability-bounded acceptance of agent-authored code, ENFORCED ("Rust Rigor, Ruby Velocity"). LLM/agent code is untrusted by construction; you cannot read every diff a fleet produces. Garnet's answer is a machine-checkable, sealed capability-diff GATE wired into an autonomous accept/reject loop (`agent-loop`) that wraps the real subcommands (wrap-don't-rebuild), so the gate cannot drift from what it accepts under. The enforced scope is honestly NARROW: only `@caps` (fs/net/env/proc) and `@max_depth` are enforced, on BOTH the interpreter (`garnet-interp-v0.3/src/eval.rs` require_capability/require_entry_capability at each host primitive in `stdlib_bridge.rs`) and the VM (entry-frame gating + `garnet-vm/src/caps_recheck.rs` cross-IR laundering trap); seccomp is Linux-only; `@bounded` (Wasmtime fuel), memory, time, `@mailbox`, and macOS/Windows OS-sandbox are DECLARED-NOT-ENFORCED. The value is precisely the boundary between what it enforces (small, proven by deterministic traps + tests) and what it merely declares — and the discipline of never blurring the two.

VS OTHER LANGUAGES: RUST memory safety is the credibility model Garnet must emulate — credible via an independent dynamic oracle (Miri), a machine-checked model (RustBelt/Coq), a decade of adversarial ecosystem pressure, and an honestly-policed boundary (`unsafe`). But safe Rust says nothing about AUTHORITY: `std` is ambient — safe code can open every file, spawn processes, exfiltrate over the network. Garnet targets exactly that gap. OBJECT-CAPABILITY LANGUAGES (E, Austral, Pony) are closest in spirit — authority only via unforgeable references, often with cleaner type-theoretic discipline (Austral's linear capabilities, Pony's reference capabilities) than Garnet's annotation-plus-runtime-trap approach — but they are languages, not ACCEPTANCE PIPELINES: none ships a sealed capability-DIFF gate answering "what NEW authority does this agent change grant?" failing CI on a widening, nor an autonomous loop wrapping the real toolchain. WASI/WASMTIME is the deployment-time peer: a real, independently-audited, runtime-enforced deny-by-default sandbox — but it bounds a MODULE at its host boundary at run time; it does not give a source-level, per-function declared-capability SURFACE a reviewer/gate can DIFF between two revisions of agent-authored source before acceptance. Garnet honestly does NOT claim Wasmtime-grade sandboxing (`@bounded` is declared-not-enforced). NET: each comparator owns a piece (memory discipline / ocap theory / runtime sandbox); Garnet's bet is the agent-acceptance integration — weaker on language-theoretic purity, uniquely targeting the diff/acceptance/agent surface.

The gold-standard bar for a security kernel

The gold-standard bar for verifying a security kernel — the bar Garnet must clear to sit beside Rust memory safety — has six elements; Garnet meets them only partially today (honestly noted):

1. INDEPENDENT ADVERSARIAL AUDIT — verification by a party with NO shared state and NO conflict of interest, motivated to break the kernel. Garnet: S114 was Claude-internal; the Codex pass is the FIRST genuinely model-lineage-independent attempt. THIS is the gap S114-independent closes.
2. EXPLICIT THREAT MODEL — written down and RE-DERIVED, not inherited: adversary = an agent authoring untrusted source the autonomous loop may accept; controls source, annotations, file layout, impl/module/actor nesting; kernel must guarantee no undeclared authority is exercised and no silent widening is sealed.
3. ATTACK-SURFACE ENUMERATION — systematic, not ad-hoc: the diff-caps widening gate, the agent-loop acceptance gate, the runtime `@caps` trap (fs/net/env/proc) on BOTH backends, the `@max_depth` trap on both backends, the static `check` caps-coverage, the seal/manifest, the caps-log, and (Linux) seccomp. CRITICAL CORRECTION TO THE S114 TEMPLATE: the surface derivation `collect_cap_fns` (capability_surface.rs:36-43) has exactly THREE descent arms — `Item::Fn`, `Item::Impl(block.methods)`, `Item::Module` — while the parser's `Item` enum (garnet-parser-v0.3/src/ast.rs) has TWELVE variants (Use, Module, Memory, Actor, Struct, Enum, Trait, Protocol, Impl, Fn, Const, Let). A catch-all swallows the other 9. Enumeration must be over the 12 variants vs the 3 arms, judging per-variant whether the interpreter can enforce `@caps` from a function it hosts.
4. REGRESSION TRAPS FOR EVERY FOUND HOLE — met: the HIGH impl-method fix has `impl_method_caps_are_in_the_surface` + `nested_module_fn_caps_are_in_the_surface`; the VM laundering trap has `planted_laundering_call_is_trapped`; `garnet_red_team_status.py` statically asserts the fix substrings + test names + honesty anchors stay present.
5. SKEPTICAL REFEREE WITH NO CONFLICT OF INTEREST — re-classifies every claim HELD / HOLE / DECLARED-NOT-ENFORCED and rejects over-claims. S114 had such a referee, but it was Claude; the independent bar requires the Codex referee (no shared state), with Opus's pass labeled review-of-the-independent-verdict, not the referee.
6. FORMAL/SEMI-FORMAL REASONING ABOUT THE CORE INVARIANT — a rigorous argument that the capability SURFACE the gate consumes EQUALS the authority the runtime ENFORCES (surface ⊇ enforced: no enforced-but-invisible function). The S114 HIGH was exactly a violation (impl-method `@caps` enforced yet invisible). caps_recheck.rs is a step toward it (a one-directional lowered ⊆ declared containment trap), NOT a full equivalence proof. This is the most important and least complete element. Garnet clears 3-5 at prototype grade, has a partial 6, and the Codex pass supplies the missing 1.
