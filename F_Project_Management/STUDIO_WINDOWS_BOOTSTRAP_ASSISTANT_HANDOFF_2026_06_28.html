Garnet Studio Windows Bootstrap Assistant Handoff

This artifact documents the Windows-side Studio change that turns CLI Health from a passive "not found" panel into an actionable bootstrap assistant. The implementation generates local, operator-run PowerShell scripts into the dogfood evidence root. It does not run installers silently, call provider APIs, include source by default, or widen the Tauri permission surface.

Problem

Clean Windows installs could launch Garnet Studio, but the first useful screen often reported: Garnet CLI not found, repository not found, and Python not found. That was honest, but not operational. A user needed an in-app path from missing prerequisites to a reproducible local setup without pretending the GUI had completed work it had not performed.

Implemented Surface

Health Model

Added BootstrapPlan and BootstrapRequirement so the backend maps current CLI Health into machine-readable setup steps.

Evidence Writer

Added studio_bootstrap_write_scripts, which writes a timestamped bootstrap-setup evidence bundle with a manifest, plan JSON, README, and scripts.

GUI Assistant

Added a CLI Health "Setup Assistant" with prerequisite chips, a refreshed plan, and a "Generate Setup Scripts" action.

Generated Files

File Purpose Honesty Boundary
bootstrap-plan.json Machine-readable copy of the detected prerequisites and setup actions. Reflects current host detection only; not a completion claim.
README.md Operator sequence for Python, repo, CLI build, env vars, and recheck. Explicitly says scripts must be inspected and run by the operator.
install-python-winget.ps1 Installs Python with winget if Python is missing. Generated only; Studio does not execute winget.
build-garnet-cli-from-repo.ps1 Builds garnet-cli, stages garnet.exe, and sets GARNET_CLI. Requires a local checkout and Cargo; no network clone is attempted.
configure-garnet-env.ps1 Sets user-scoped GARNET_REPO, GARNET_CLI, and PATH. Fails if paths do not exist.
run-bootstrap-preflight.ps1 Prints detected Python, Cargo, Garnet, winget, env vars, host, and arch. Observation only.

Seven-Pass Review Loop

  1. Contract pass: Confirm no shell plugin, opener plugin, provider path, or Tauri capability broadening.
  2. Health pass: Confirm missing CLI/repo/Python become actionable requirements, not vague errors.
  3. Windows pass: Confirm PowerShell scripts use user-scoped env vars and fail on missing paths/tools.
  4. Evidence pass: Confirm generated scripts land under Desktop/dogfood/garnet-studio-windows-linux with MANIFEST.sha256.
  5. UI/UX pass: Confirm the assistant is visible from CLI Health and does not crowd core parse/check/run controls.
  6. Test pass: Run Studio Rust tests, Python contract tests, status tests, and frontend build.
  7. Mac continuation pass: Reproduce the same UX semantics on macOS without changing Windows evidence claims.

Mac Studio Continuation Notes

The Mac-side follow-up should keep the same assistant semantics: render a prerequisite plan, write local setup evidence, and keep generated bootstrap commands separate from actual execution. macOS-specific install scripts can be added later, but any claim of "installed" must come from a reproduced launch/check proof, not from script generation.

Recommended next check: launch Studio from this branch on Windows, press "Generate Setup Scripts", inspect the generated bundle, then run CLI Health again after any operator-executed setup steps.
