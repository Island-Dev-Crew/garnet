# Garnet Manifest v0.1

Date: 2026-05-20 (v0.5.1, slice S3)
Status: minimum-viable manifest + lockfile spec
Owner: `garnet-cli/src/cmd/add.rs`

This document defines the on-disk format of `Garnet.toml` (the
project manifest) and `Garnet.lock` (the content-addressed lockfile) at
v0.5.1. The format is intentionally narrow: it covers what `garnet add`
writes today plus the minimum surface that the existing CLI templates
already expect.

The spec is `v0.1` because the resolution semantics are not finalized
yet (see § Honest Partials). A `v1.0` of this document will lock in the
resolver contract once `garnet run` consumes `[dependencies]` at
runtime.

---

## 1. `Garnet.toml` — the project manifest

`Garnet.toml` lives at the project root. It is plain TOML 1.0 (RFC).
The schema relevant to dependencies is:

```toml
[package]
name = "my-app"
version = "0.1.0"
edition = "garnet-0.3"

[dependencies]
# Each dependency is a single key with an inline-table value.
mylib = { path = "../mylib", vendor = ".garnet/vendor/mylib" }
```

### 1.1 `[package]` table

- `name` (required, string) — the project's identifier.
- `version` (required, string) — SemVer-compatible. v0.5.1 does NOT
  enforce SemVer beyond a string equality check; resolver work is
  deferred.
- `edition` (required, string) — the Garnet language edition. v0.5.1
  templates pin `garnet-0.3`.

### 1.2 `[dependencies]` table

Each key is a dependency name (matches `[A-Za-z_][A-Za-z0-9_-]*`).
Each value is an inline table with:

- `path` (required, string) — the user-facing source. May be relative
  (resolved against `Garnet.toml`'s parent) or absolute. v0.5.1 supports
  local paths only; remote schemes (`https://`, `git+ssh://`, registry
  shortnames) are deferred.
- `vendor` (required, string) — the in-project vendor location, always
  `.garnet/vendor/<name>`. `garnet add` writes this; users should not
  edit by hand.

Optional keys recognized by v0.1 but ignored by tooling today:

- `version` (string) — recorded for forward compatibility with the
  future resolver.
- `optional` (bool, default `false`) — also reserved.

### 1.3 Other tables

`[caps]`, `[build]`, `[[bin]]`, etc. are out of scope for this spec;
see the project-template `Garnet.toml` under
`garnet-cli/templates/*/Garnet.toml`.

## 2. `Garnet.lock` — the content-addressed lockfile

`Garnet.lock` lives next to `Garnet.toml`. It is generated by
`garnet add` and is plain TOML 1.0. The schema:

```toml
# Garnet.lock — generated by `garnet add`. Do not edit by hand.
version = "0.1"

[[dependencies.mylib]]
path = "../mylib"
vendor = ".garnet/vendor/mylib"
files = [
  { path = "lib.garnet", hash = "8a7c..." },
  { path = "nested/util.garnet", hash = "33d4..." },
]
```

### 2.1 Top-level keys

- `version` (required, string) — the lockfile schema version. v0.5.1
  writes `"0.1"`.

### 2.2 `[[dependencies.<name>]]` array-of-tables

One block per dependency. The block name's `<name>` MUST match a key in
`Garnet.toml`'s `[dependencies]` table.

- `path` (required, string) — the source path recorded at vendor time.
  Matches `Garnet.toml`'s `path` field.
- `vendor` (required, string) — the in-project vendor location. Matches
  `Garnet.toml`'s `vendor` field.
- `files` (required, array of tables) — one entry per regular file
  found under the vendor tree, sorted by `path`. Each entry has:
  - `path` (string) — the file path relative to the vendor root.
  - `hash` (string) — lowercase hexadecimal **BLAKE3** digest of the
    file's bytes.

### 2.3 Determinism guarantees

`garnet add` writes `Garnet.lock` in a stable order:

- Dependencies sorted alphabetically by name.
- Files within a dependency sorted lexicographically by `path`.
- Hashes always lowercase hex.

Re-running `garnet add` on an unchanged source produces a byte-identical
lockfile.

## 3. Lifecycle: how `garnet add` uses these files

1. User runs `garnet add ../mylib`.
2. The command finds the nearest `Garnet.toml` by walking upward.
3. It copies the source tree into `.garnet/vendor/<name>/`, skipping any
   nested `.garnet/` and `Garnet.lock` files in the source.
4. It hashes every regular file in the vendor tree with BLAKE3.
5. It writes `<name> = { path = "...", vendor = ".garnet/vendor/<name>" }`
   into `[dependencies]`, replacing any prior entry with the same key.
6. It writes `Garnet.lock` with the dep's per-file hashes, replacing
   any prior `[[dependencies.<name>]]` block.

## 4. Honest partials (v0.5.1)

The spec is `v0.1` because these are **explicitly deferred** to a
later slice:

- **Resolver contract.** v0.5.1 does NOT define how `use <dep>::<sym>`
  resolves at parse/check/run time. The vendored bytes sit on disk and
  `Garnet.lock` records their hashes, but the interpreter does not yet
  load them into the symbol table.
- **Remote sources.** v0.5.1 supports local paths only.
- **Transitive deps.** If a vendored dependency itself has a
  `Garnet.toml`, its deps are NOT pulled in.
- **SemVer matching.** A `version` field is recorded for forward
  compatibility but no equality, caret, or tilde matching happens at
  add time.
- **Workspace mode.** Multi-crate workspaces are out of scope.
- **Lockfile reconciliation.** If the source tree changes underneath
  without `garnet add` rerunning, `Garnet.lock` will be stale. A future
  `garnet verify-deps` (separate slice) reports drift.

These partials are tracked in `scripts/garnet_mit_readiness_status.py`'s
"Garnet manifest + vendored deps" lane.
