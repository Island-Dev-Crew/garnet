What @caps is, and why every function should declare its authority

Start with the bug class. Nearly every supply-chain incident of the last few years — the typosquatted package, the hijacked maintainer account, the post-install script that phones home — works because of one default: code can do anything the process can do. A left-pad-sized utility has the same authority as your deploy script. Signatures don't fix this; the industry has already shipped validly-signed malware. A signature tells you who published the code. It says nothing about what the code is allowed to do.

That default has a name — ambient authority — and @caps is Garnet's refusal of it.

Before and after

Here is a function that declares a network budget and then quietly reaches for the filesystem — the shape of every "the update added a little something extra" incident:

@caps(net)
def sneaky() {
  fs::read_file("/etc/passwd")
}

And here is the compiler refusing it — this is real output, not a mock-up:

$ garnet check
caps coverage: function `sneaky` does not declare `fs`
but transitively calls `fs::read_file` which requires it

The check is transitive across the call graph: if main calls helper calls fs::read_file, somebody on that chain has to have declared fs, and the entry point must declare its own budget. The propagator runs at compile time. At run time, capability primitives trap if the calling chain never declared the authority — on both execution backends, with cross-OS trap parity recorded as evidence rather than asserted.

Why this matters more now

AI agents write more of the code every month, and the honest bottleneck has moved to review. A reviewer staring at a 4,000-line agent-authored diff cannot hold every line in their head — but they can hold one question: did this change grow what the code is allowed to do? Because every function carries its budget, Garnet's diff-caps answers that mechanically: the authority delta of a change, on one screen. Same-or-narrower authority is a fundamentally different review than "now also wants the network."

Isn't this just sandboxing?

Closest prior art, credited gladly: the Wasm Component Model and WASI scope imports at module boundaries; OS sandboxes (seccomp, pledge) scope the process; object-capability research worked out the theory decades ago. @caps differs in granularity and address: it lives inside the language, per function, where the review happens — so the unit of "what can this do" matches the unit of "what did the agent just change." The boundary technologies compose with it; a future backend lowering can hand @caps straight to WASI scopes and engine fuel. That synergy is one reason the backend decision leans integrate-don't-rebuild.

The honest boundaries

Garnet is a research-grade prototype, and this post claims exactly what the gates prove: @caps and @max_depth trap deterministically on both backends; seccomp application is Linux-only; macOS/Windows OS-sandbox enforcement, Wasmtime fuel for @bounded, and memory/time/mailbox ceilings remain declared-not-enforced; and the one HIGH red-team finding against the kernel was self-found and self-fixed — independent re-verification is queued, and until it lands we say "self-verified," not "audited." No production claims. That discipline is the same idea as @caps itself: no authority without evidence.
